# 第二轮机制复审 · 2026-10-06

基线：ff8f96b，Godot 当前可玩首关。运行时代码未修改；只保留此报告、复现脚本与日志。原处决误杀与完美属性生命周期修复仍在；本轮针对范围提示、继续路径和扩容站位补充边界复现。未重跑并宣称整个回归套件。

## P2 · 缺字段检查点能通过检查，却恢复报错

run_controller.gd:198 对 upgrade 使用 get 默认空串，该值在合法列表；但 resume:229 直接读取 c.upgrade。合法检查点删除 upgrade 后 can_resume=true，调用 resume 实际报 Invalid access to property or key upgrade，停在 phase=cleared / room=v0。

正常新存档会包含该字段；触发条件是缺字段、旧结构或被编辑的检查点，不是所有继续操作都失败。建议统一纯函数校验/规范化全部检查点字段，先得到完整恢复数据再重建场景；无法恢复时保留原档，尝试可用备份。测试必须覆盖每个必需字段缺失与错误类型。

## P2 · 处决提示与实际命中条件不一致

combat.gd:12 选目标只检查残血和62距离，未检查纵深、临时无敌或空中资格；实际 resolve 使用执行动作命中框和防御窗口。复现 hero=(200,430)，残血刀妖=(210,480)，距离50.99，选为处决目标；两者静止，正常输入推进35帧后 HP仍8、executes=0。

建议处决提示与实际触达共用资格判定，至少加入纵深和空中/无敌状态；若要做带短突进的处决则明确位移与追踪规则。重点验证侧向、纵深、空中、无敌、正在逃离及起手后状态变化。

## P2 · 九只小兵复用六个等候位置

enemy_director.gd:101 的纵深按 index%3，前后排按 int(index/3)%2，两者每六只重复。实际房间第三场 actor index1与7，在相同玩家侧、相同采样位置且无攻击名额时，intent完全相同（-0.729537,-0.683941），表示争用同一等候位置。

建议为存活等候者分配唯一位置，攻击者离开后释放位置，死亡后平滑重排；避免依赖孩子序号反复取模。保留用户认可的总人数和两个攻击名额。此复现证明位置复用；没有据此宣称已测量画面抖动或性能下降。

## 体验优化 · 胜利后待领取状态不保存

存档明确只存房间入口，loot阶段尚未claim_loot时没有新的胜利检查点。复现正式清场状态由loot返回首页后继续，变成fighting，Boss和三护卫全数恢复（alive=4）。脚本设置敌人HP=0以隔离结算路径，不是正常通关难度样本。

属于已说明的房间入口继续设计，但正常退出/闪退发生在领取遗物前会要求重打Boss。建议在Boss清场进入loot时存待领取状态；重启继续打开遗物面板，领取与成绩更新一次结算。

## 体验优化 · Boss 控制抗性尚未区分

yone_skills.gd:134 调用target.launch，没有区分boss或superArmor；actor.launch无条件change(hit)。Boss在带superArmor的bossNova中被windRush击中，会退出原招式进入hit并硬直30帧。可以是允许技能破霸体的设计，不列为确定漏洞，也未证明无限控制。

建议明确规则：普通怪完整击飞，Boss缩短控制时间或仅在特定招式可打断；保留技能命中收益和反击窗口。实际控制强度需要真人对战样本，不建议仅为“更难”直接让Boss免疫全部控制。

## 建议处理顺序

检查点规范化 → 处决提示/命中一致 → 唯一等候位置 → 胜利待领奖保存 → Boss控制强度试玩调参。

证据：probe.gd、probe.log。脚本使用隔离的内存进度，不触碰玩家真实存档；预期恢复错误记录在日志中，因此进程退出0不代表这是一轮通过的测试。本轮未修改或提交游戏实现。
